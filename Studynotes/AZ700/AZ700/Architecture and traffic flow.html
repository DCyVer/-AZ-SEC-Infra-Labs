(0)Global Topology Assumptions:
Unless an item's (modifier) or //*Comment explicitly states otherwise, the following AZ-700 "Success States" are assumed true. 
  • Vnet Peering on hub spokes assumes the following are enabled
    'Allow Transit' on the peering link from the source Hub vNet 
    'Use Remote Gateway' on the peering link from the Spoke vNet
    'Forwarded Traffic" if routed through NVA/Firewall

  •  ER/VPN Gw's / GlobalReach assume BGP Route propagation enabled on GatewaySubnet  

  • Vnet Injection assumes “Subnet Delegation” is active on the destination resource 

  • BackendPool assumes “Healthy” probes

  • AVNM assumes that traffic rule for that path is set to either allow or always allow

  • NSG/ASG: assumes that traffic rule for that path are set to allow

[SALVAGE 2] // Spoke-to-Spoke Hairpin (!fwd-ed Traffic!)

  • The Scenario: Traffic between spokes must be scrubbed by the Firewall. In AZ-700, this requires a specific handshake in the Firewall logic.

  • Surgical Twig: [Regional⁴][Prvt.²][Int.(server)¹] [HUB-SPOKE] (←||→) [vNet peering⁷] → [UDR¹³] → [Az. FW¹⁶] (!fwd-ed Traffic!) → [vNet peering⁷] → (←||→) [NIC(VM)⁸]

[SALVAGE 3] // The Global Peering "FAIL" (Critical Exam Trap)

  • The Scenario: Attempting to use GlobalGwTransit across a Global vNet Peering bridge.

  • The Fact: Traditionally, Global Peering does not support GlobalGwTransit. If an exam question asks to use a remote gateway over a global bridge, the answer is "Infeasible."
