DNS

INSTANT DECISIONS
"Private Link resolving to Public IP" ➔ Missing vNet Link or Private DNS Zone Group.
"Azure VM cannot find .local" ➔ Forwarding Ruleset not linked to vNet.
"On-prem cannot see Azure Zone" ➔ Inbound Endpoint IP missing from On-prem Conditional Forwarder.
"FQDN Filter fails (Az Firewall)" ➔ Enable DNS Proxy + Point vNet DNS to Firewall IP.
"Windows VM (Custom DNS)" ➔ Obsolete/Inefficient ➔ Use Azure Private DNS Resolver.


THE DNS RESOLUTION SEQUENCE (THE PING)

  1. Stored (Local Cache -/ Hosts) 

  2. No cache? → DNS Proxy (Firewall)

  3. No FwProxy → VNet Link →

    1. Fwd Ruleset (corp.local) match associated Endpt out (DNS Private Resolver) → (onPrem.)

    2. no match? → Private DNS Zone 

  4. No VNetLink? → Public DNS > Return public IP (implicit Fw Deny applies to internet traffic) 

  5. Public Inet accessible?  (Split-Horizon )

    → internal → Private IP (via Zone Link),

    external → Public IP (Azure Recursive Resolver (168.63.129.16)

//Private DNS Zones use A records for Private Endpoints. Use CNAMEs to alias the public service name to the private link name.
 

CNAME: PaaS service (e.g., blob.core.windows.net) (← CNAME to the .privatelink. sub-domain) → Private DNS Zone.

Cross-VNet: Hub Resolver serves spokes with vNet links in it's forwarding ruleset

Private DNS Zone [Microsoft.Network/privateDnsZones]
Resolves: privatelink namespaces | Max: 100k records. ➔ A (Private Endpoint) | CNAME (Alias) | PTR (Reverse).
Reverse DNS (PTR): Private DNS Zones support PTR records; required if the app does a reverse lookup of the Private Endpoint IP. ! Private DNS Zone namemust follow the in-addr.arpa format (e.g., 10.in-addr.arpa).

vNet Link: Connects vNet to Zone | Limits/Zone: 1k Links (100 Auto-Reg) | Limits/vNet: 1 Auto-Reg Zone max.
Zone Group: Auto-Syncs Endpoint IPs to A-records | Role: Network Contributor on the Zone.

//Zone Group sync, requires user/ID Network Contributor role onPrivate DNS Zone resource
