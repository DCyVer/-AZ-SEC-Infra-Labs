### “TWIGS” ###
Structural Definition
Branches: Categorical containers. They define the Native Header Items and the Twigs within them.
Twigs: Sequential chains representing segments of a 1:1 validated circuit (AZ-700 curriculum).
Coverage: Every item in a Branch Header must appear in at least one twig. Each item represents a single link/step in the traffic journey. All items in all twigs are inhereted from branch headers and may have modifiers
2. The Logic of the Chain (Traceability)
Forward Trace: Entry points must be a valid exit/hand-off from a previous logical step.
Backward Trace: Every terminal item in Branch 8 must reconcile back to a Branch 1 Source.
Sidechannel: a chain can have a sidechannel where data does not pass through, for instance a DNS or authentication. 
Deterministic Circuit: No generative steps. If a branch starts/ends in another branch, those branches must contain matching twigs that align perfectly without gaps.
Circuit Bounds: The first link is always Source (Br 1); the last link is always Destination (Br 8). they can be spread accross branches. 
3. Twig Entry/Exit Mechanics
Entry Points: A twig has exactly one entry point (defined by one or more items from other branches that determine the unique set of switches for that that path. the minimum amount of item and modifier  identifiers that narrow down to that specific twig should be used
Exit Points: A twig can have multiple exit points.
Termination: A twig terminates if it reaches Destination (Br 8) or a Hand-off (an item from another branch that eventually leads to a destination).
The Double-Fork Rule: If a route forks more than once, the twig must terminate at the second fork item (e.g., [Az FW¹⁴], [AppGw¹¹]) and hand off.
Non-Linearity: Exit points do not have to move "forward" (e.g., hair-pinning loop-back to Branch 7 is valid).
Side-Channels: Represent non-passing data (DNS, Auth, Routing) via (⟷ [Item^#]).
4. Formatting for Termination
If all twigs at an exit point terminate without further branching, use: [ <path to termination> | <path2> ].
5. Validation:  Twigs and their content should never be generated, but always traced and validated from source to destination and fully representative of the AZ700 exam curriculum and the existing items and branches of the tree
Twigs should always be self explanitory, follow system logic and represent the entry points and exit points that suit their networking function. If a necessary item does not exist, any additional inclusion or modification must be mutually agreed upon. no exceptions.
